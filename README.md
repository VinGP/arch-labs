# Лабораторные работы №1–2: групповой чат

Проект реализует групповой чат через Java API без сетевого сервера. Клиенты работают в разных потоках одного JVM-процесса.

## Требования и запуск

- JDK 22;
- Maven 3.9+.

```shell
mvn test
```

## Использование

Лабораторная №1 хранит состояние в памяти:

```java
ChatServer server = new ChatServerImpl(new InMemoryChatStorage());
```

Лабораторная №2 использует файловую H2:

```java
var storage = new H2ChatStorage("jdbc:h2:file:./data/chat;DB_CLOSE_ON_EXIT=FALSE");
ChatServer server = new ChatServerImpl(storage);
```

Клиент подключается через `ChatSession`:

```java
var inbox = new ArrayList<Message>();

try (var ivan = server.connect("ivan", inbox::add)) {
    ivan.send("Привет!");
    ivan.setNotificationsEnabled(false);
    List<Message> history = ivan.history();
}

server.close();
```

Сообщение доставляется всем подключённым пользователям с включёнными уведомлениями, включая отправителя. Историю можно запросить после отключения уведомлений. Повторное одновременное подключение одного имени запрещено.

## Метрики Prometheus

Счётчики регистрируются один раз в глобальном реестре
`PrometheusRegistry.defaultRegistry`. Интерфейс `ChatServer` не зависит
от Prometheus, передавать реестр в конструктор не требуется:

- `chat_requests_total` — количество успешно выполненных пользовательских
  операций: подключение, чтение состояния, отправка сообщения, настройка
  уведомлений, чтение истории и отключение;
- `chat_notifications_total` — количество успешных вызовов обработчика доставки
  сообщения. Доставка одного сообщения двум пользователям считается двумя
  оповещениями. Ошибки обработчика, отключённые пользователи и пользователи
  с выключенными уведомлениями счётчик не увеличивают.

Отклонённые операции и повторное закрытие сессии не считаются запросами.
Чтение метрик и закрытие сервера также не увеличивают счётчик запросов.
Счётчики потокобезопасны и суммируют события всех экземпляров чата в одной JVM.
Создание или закрытие сервера, в том числе повторное открытие H2 в том же
процессе, не сбрасывает значения. Счётчики начинаются с нуля при запуске
новой JVM; их значения не сохраняются в H2.

Для сбора метрик запустите отдельный HTTP-экспортёр из библиотеки Prometheus:

```java
import io.prometheus.metrics.exporter.httpserver.HTTPServer;

try (var exporter = HTTPServer.builder()
        .hostname("127.0.0.1")
        .port(9400)
        .buildAndStart()) {
    // Работа клиентов через Java API; экспортёр живёт до выхода из блока.
}
```

Метрики доступны по адресу `http://127.0.0.1:9400/metrics`.
Экспортёр запускается явно, обычное создание чата сетевой порт не открывает.
Конфигурация для Prometheus, запущенного на той же машине:

```yaml
scrape_configs:
  - job_name: arch-labs-chat
    static_configs:
      - targets: ['127.0.0.1:9400']
```

Общие тесты обоих хранилищ проверяют, что глобальный реестр собирает метрики
`chat_requests` и `chat_notifications`. При экспорте счётчиков к именам
добавляется суффикс `_total`. HTTP-экспорт и точные значения счётчиков
пока не проверяются.

## Структура

- `ChatServer` — интерфейс сервера чата;
- `ChatServerImpl` — потокобезопасная реализация координации сессий и доставки;
- `ChatSession` — интерфейс клиентской сессии;
- `InMemoryChatStorage` — хранилище лабораторной №1;
- `H2ChatStorage` — транзакционное хранилище лабораторной №2;
- `ChatServerContractTest` — общий набор сценариев для обеих реализаций;
- `H2RestartTest` — штатный и нештатный перезапуск.

## Контрольные вопросы

### Как имитируется одновременная работа разных клиентов?

В приложении каждый клиент представлен объектом `ChatSession`, а в тесте
`ChatServerContractTest.concurrentClientsDoNotLoseMessages` клиенты запускаются в
разных потоках:

1. `Executors.newFixedThreadPool(2)` создаёт два рабочих потока.
2. Через `submit` в них запускаются задачи клиентов `ivan` и `andray`.
3. Каждый клиент самостоятельно подключается к одному экземпляру `ChatServer`.
4. `CyclicBarrier(2)` задерживает оба потока до готовности и затем одновременно
   разрешает им отправлять сообщения.
5. Каждый клиент отправляет по 100 сообщений.
6. Вызовы `Future.get(5, TimeUnit.SECONDS)` ожидают завершения задач, передают в
   тест исключения из клиентских потоков и не позволяют тесту зависнуть навсегда.

После завершения потоков тест проверяет, что в истории находятся все 200
сообщений, их идентификаторы идут без пропусков от 1 до 200, а от каждого
отправителя сохранено ровно по 100 сообщений. Значит, тест проверяет не просто
запуск нескольких потоков, но и отсутствие потерь данных при их конкуренции.

Потокобезопасность реализована в `ChatServer`: операции подключения, отправки,
изменения настроек, чтения истории и отключения защищены `synchronized (this)`.
Поэтому общая карта активных сессий и выбранное хранилище изменяются
последовательно. Обработчики доставки вызываются уже после выхода из
синхронизированного блока, чтобы медленный или ошибочный клиент не удерживал
блокировку сервера. Один и тот же контрактный тест наследуют
`InMemoryChatServerTest` и `H2ChatServerTest`, поэтому сценарий выполняется и для
хранилища лабораторной №1, и для H2 из лабораторной №2.

### Как сохраняется состояние после перезапуска?

В лабораторной №1 `InMemoryChatStorage` хранит пользователей в `HashMap`, а
сообщения — в `ArrayList`. Эти данные принадлежат процессу JVM и исчезают вместе
с ним.

В лабораторной №2 вместо него используется `H2ChatStorage` с файловым JDBC URL,
например `jdbc:h2:file:./data/chat;DB_CLOSE_ON_EXIT=FALSE`. Состояние записывается
в две таблицы:

- `users`: имя, признак подключения, время последнего подключения и настройка
  уведомлений;
- `messages`: идентификатор, отправитель, текст и время отправки.

Интерфейс `ChatStorage` отделяет логику чата от способа хранения. Поэтому
`ChatServer` и `ChatSession` не меняются: при запуске достаточно передать серверу
`H2ChatStorage` вместо `InMemoryChatStorage`.

При повторном запуске создаётся новый `H2ChatStorage` с тем же JDBC URL. Команда
`CREATE TABLE IF NOT EXISTS` сохраняет существующие таблицы, после чего методы
`user()` и `history()` читают уже записанные строки. Настройки уведомлений,
история и время последнего подключения поэтому восстанавливаются.

Признак `online` намеренно сбрасывается в `FALSE` методом `resetOnlineUsers()`:
после перезапуска прежних клиентских потоков и объектов `ChatSession` больше нет,
следовательно, считать таких пользователей подключёнными было бы неверно.
Штатный сценарий проверяет
`H2RestartTest.restoresStateAfterNormalRestart`: первый сервер закрывается,
второй открывает тот же файл и получает сохранённое состояние.

### Как обеспечивается сохранность при нештатном завершении?

Каждая изменяющая операция `H2ChatStorage` — подключение, отключение, изменение
настроек и добавление сообщения — выполняется через общий метод `transaction()`:

1. отключается автоматическое подтверждение (`setAutoCommit(false)`);
2. выполняется вся операция;
3. при успехе вызывается `commit()`;
4. при `SQLException` или другой ошибке времени выполнения вызывается
   `rollback()`;
5. режим автоматического подтверждения восстанавливается.

Таким образом, операция сохраняется целиком либо не сохраняется вообще. В базе
также заданы первичные и внешний ключи и ограничения `NOT NULL`, которые не дают
записать внутренне противоречивые данные.

Команда H2 `SET WRITE_DELAY 0` отключает отложенную запись подтверждённых
изменений. После успешного `commit()` H2 записывает необходимые данные журнала
на диск, а при следующем открытии файла выполняет восстановление. Завершившаяся
до `commit()` транзакция будет отменена, а уже подтверждённая — сохранена.

Это проверяет `H2RestartTest.restoresCommittedStateAfterAbnormalExit`. Тест не
вызывает `ChatServer.close()`, а выполняет `SHUTDOWN IMMEDIATELY`, имитируя
аварийную остановку H2. Затем база открывается заново и тест сравнивает историю,
настройку уведомлений и время последнего подключения с состоянием перед аварией.

### На что влияет сохранение состояния в хранилище?

Сохранение состояния влияет на следующие свойства программы:

- **Надёжность.** Пользователи, их настройки и сообщения переживают штатный и
  нештатный перезапуск процесса. Незавершённые изменения не оставляют частично
  обновлённое состояние.
- **Производительность.** Вместо изменения коллекций в памяти выполняются SQL,
  дисковый ввод-вывод и `commit`. Настройка `WRITE_DELAY 0` повышает надёжность
  подтверждённых записей, но увеличивает стоимость каждой изменяющей операции.
- **Параллельная работа.** В этой реализации `ChatServer` последовательно
  выполняет обращения к одному JDBC-соединению под своей блокировкой. Это делает
  доступ корректным для нескольких клиентских потоков, но ограничивает
  пропускную способность одним изменением состояния за раз.
- **Модель данных.** Появляются таблицы, типы столбцов, ключи и ограничения,
  которые нужно поддерживать при дальнейшем изменении приложения.
- **Обработка ошибок и жизненный цикл.** Ошибки JDBC преобразуются в
  `StorageException`, неуспешные транзакции откатываются, а соединение требуется
  закрывать.
- **Тестирование.** Общие функциональные сценарии запускаются для обоих
  хранилищ, а для H2 дополнительно проверяются штатный и аварийный перезапуски.

При этом публичный Java API чата от способа хранения не зависит: клиент по-прежнему
работает через `ChatServer` и `ChatSession`. Меняется только переданная реализация
`ChatStorage`.
